## Журнал исходных решений

| ID | Решение | Почему | Когда пересмотреть |
|---|---|---|---|
| ADR01 | Адаптивное веб-приложение | Один клиент для телефона и компьютера, быстрее проверить сценарий | Нативная функция доказанно блокирует использование |
| ADR02 | Модульный Django + React | Один backend с общими правилами, Python рядом с медиа | Измеренный предел, а не желание микросервисов |
| ADR03 | Private filesystem через StorageAdapter | Один пилот, простое развёртывание и контроль | Несколько узлов, большие объёмы, отдельная оценка S3 |
| ADR04 | DB jobs + Celery broker | Состояния и идемпотентность принадлежат приложению | Только после подтверждённой проблемы выбранного механизма |
| ADR05 | Manual D0 перед AI D1 | Пользовательский процесс можно проверить независимо от модели | Не отменять ручное исправление при росте качества |
| ADR06 | Речь и evidence-сегменты, без полной видеоаналитики | Понятная привязка к источнику и ограниченный объём | Есть разрешённый набор молчаливых действий и измеримый выигрыш CV |
| ADR07 | Публикация человеком и immutable snapshot | Ошибки ИИ не становятся незаметно рабочими указаниями | Автопубликация не входит в текущий план |
| ADR08 | Внешний provider по умолчанию выключен | Пока не определены данные, бюджет и поставщик | Зафиксированы условия конкретной организации |
| ADR09 | RU интерфейс, KK ASR отдельно оценивается | Нельзя переносить результат одного языка на другой | После независимого KK набора и перевода интерфейса |
| ADR10 | Три владельца, дополнительные люди необязательны | Подтверждённая команда — трое | Человек действительно присоединился и имеет доступные часы |
| ADR11 | GPT‑6 Astra как помощник разработки | Это сообщённый пользователем способ работы | Производственный provider выбирается отдельным решением |
| ADR12 | Первый пилот — простые операции одной компании | Доступный контроль результата и содержания | Подтверждена польза, есть следующий реальный процесс |

## Что требуется решить в ходе разработки

| Вопрос | Владелец | Блокирует | Действие, доступное пока решения нет |
|---|---|---|---|
| Кто A/B/C и сколько часов | Команда | Надёжную дату релиза | Документы, прототип и первые маленькие задачи |
| Партнёр, операция, проверяющий | A | Реальный пилот и подтверждение спроса | Собственные деморолики, интервью по разрешению |
| Можно ли хранить и передавать материал | Владелец данных + C | Загрузку реальных данных и external AI | Локальные синтетические/собственные fixtures |
| Сервер, регион, бюджет, аккаунт | B + владелец оплаты | Общий staging/pilot | Local development и измерение ресурсов |
| Доступный API составления шагов | C + B | Реальную автоматическую генерацию | Fake/Disabled provider, ручной редактор |
| Условия почтовой отправки | B | Приглашения вне локальной среды | Локальный почтовый sink для разработки |
| Сроки хранения/удаления | Компания + B | Передачу рабочих материалов | Предлагаемая политика 07 и механизм удаления |
| Качество RU/KK/mixed | C + мастер | Обещание автоматической поддержки языка | Ручное создание, экспериментальная маркировка |

Это не список вопросов, на которых остановлена подготовка. План уже готовится с явными допущениями. Каждая зависимая операция выполняется после соответствующего решения; остальные задачи идут независимо.

## Положение на рынке

Ранее в коллекции идей зафиксированы зарубежный прямой ориентир DeepHow и смежный казахстанский AI Router. Сам этот факт означает, что нельзя позиционировать «Опыт мастера» как гарантированно единственный продукт в мире или недоступную конкурентам идею. Отсутствие найденного местного прямого аналога не доказывает его отсутствия.

Эта версия документа — план разработки, а не новое исчерпывающее исследование рынка. Перед коммерческим предложением повторно проверить функции и доступность альтернатив для казахстанского клиента, цены, данные и текущие локальные внедрения. Сравнивать законченный сценарий и реальные ограничения, а не только наличие слова «ИИ».

Возможные направления отличия — проверяемые гипотезы: удобство для небольших рабочих команд; время от записи до утверждения; локальная терминология; понятная история версий; контролируемое хранение. Они требуют проверки пользователями и не выдаются за уже существующее преимущество.

## Правило изменения документации

При изменении scope, полей, состояний, API или ролей обновить соответствующие 01–09, задачи и критерии приёмки в одном изменении. При изменении сроков пересчитать часы владельцев и зависимости. Если новые доказательства опровергают гипотезу, сохранить факт и изменить решение; не подгонять критерии задним числом, чтобы объявить пилот успешным.
