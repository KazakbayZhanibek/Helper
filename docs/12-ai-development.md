# Как разрабатывать с GPT‑6 Astra

[К полному плану](00-overview.md)

## Роль модели и людей

Вы сообщили, что работаете с GPT‑6 Astra. В этом плане модель — инструмент команды для реализации и анализа. Наличие доступа к ней не подтверждает конкретный API, стоимость, допустимость рабочих данных или скорость разработки. Внутренний provider продукта выбирается отдельно.

A отвечает за продукт и интерфейс, B — за данные и правила сервера, C — за медиа, ИИ и проверку эксплуатации. Модель может помочь любому из них. Итог принимает человек: читает изменение, запускает проверку и подтверждает поведение. Нельзя заменить обзор одного и того же сгенерированного кода повторным ответом той же модели без запуска.

## Размер одной работы

Один запрос модели — одна проверяемая задача или её самостоятельная часть: например, save working copy с конфликтом ревизий. Не просить одновременно весь backend, весь frontend и работающий production. Для задачи длиннее рабочего дня выделить сначала контракт/миграцию, затем сервис, API и интерфейс, сохранив один сквозной критерий.

Перед началом исполнитель читает задачу из 11, ссылки на нужные разделы, текущие файлы и фактические тесты. Номер задачи не является доказательством готовности зависимостей: убедиться, что они уже реализованы. Пока существует только этот план, задачи T001–T072 остаются pending.

## Универсальный запрос на реализацию

```text
Проект: «Опыт мастера». Выполни задачу T___ из docs/11-tasks.md.
Сначала прочитай docs/00-overview.md, конкретную задачу и указанные
ниже документы: [перечислить релевантные 01–09]. Затем осмотри
текущий код, AGENTS.md и реальные команды проверки.

Цель: [наблюдаемое поведение].
Область изменений: [реальные каталоги/файлы после осмотра].
Контракт: [маршруты, схема, роли, ошибки].
Проверка: [критерии задачи и негативный сценарий].

Сохрани текущие посторонние изменения. Не выдумывай существующие API,
пакеты, результаты тестов и доступы. Не загружай внешним сервисам
материалы компании. Используй фиктивные данные. Если обнаружишь
противоречие контрактов, сначала покажи конкретные строки и предложи
минимальную поправку. Не ослабляй авторизацию, чтобы прошёл тест.

Реализуй законченную задачу, выполни уместные проверки. В конце укажи:
что изменено, какие проверки реально запущены, их результат,
оставшиеся ограничения и какие критерии пока не выполнены.
```

Это задание разработчику внутри выбранного инструмента. Оно не разрешает автоматически создавать другие чаты, делегировать агентам, публиковать сайт, покупать сервисы или отправлять сообщения компании.

## Первые задания A

**T002 — проверить маршрут до кода.** Дать модели документы 01/02. Попросить интерактивный локальный прототип «библиотека → загрузка → ручной редактор → проверка → читатель» на вымышленных данных. Обязательно состояния: пусто, загрузка, нет прав, ошибка, конфликт правок, длинный заголовок. Приёмка человеком: пройти с клавиатуры и на ширине 360 px, получить обратную связь двух будущих пользователей. Демопрототип не называть рабочей обработкой ИИ.

**T006/T015 — каркас и вход.** После выбора lock-версий попросить routing, API client, CSRF, session state и protected routes. Проверить возврат к QR-ссылке после входа, запрет внешнего next URL, видимое окончание сессии. В коде не должно быть фиктивного `isAdmin=true` вне тестовых fixtures.

**T023/T025 — редактор.** Дать OpenAPI и 02/04/05. Попросить список шагов с формой, перемещением кнопками, временем в ms, autosave 1500 ms и одним inflight-запросом. Приёмка: два окна, конфликт 412, локальный текст не исчезает; серверное подтверждение отличимо от ожидания сохранения.

## Первые задания B

**T007/T010 — backend и данные.** Дать 03/04/07. Сначала своя User-модель и пустая миграция приложения, затем tenant entities и constraints. Попросить объяснить, как предотвращается связь job компании A с asset компании B, и доказать интеграционным тестом прямой операции через ORM. Нельзя переносить всю защиту в serializer.

**T022 — сохранение.** Дать схему WorkingCopy, If-Match и пример PUT. Попросить domain service с транзакцией, валидацией времён/источников, проверкой editable/workflow и сбросом отметок изменённых шагов. Отдельно проверить удаление шага с review comment и перестановку ordinal без кратковременного unique conflict.

**T028 — публикация.** Дать транзакцию 04 и тесты PUB01–PUB04. Попросить неизменяемый snapshot, блокировки, монотонный version_number, current pointer и идемпотентность. Приёмка: два одновременно отправленных publish; ровно одна версия и никакой случайной публикации нового черновика.

## Первые задания C

**T009 — эталонные материалы.** Попросить подготовить шаблон ручной разметки и генераторы безопасных медиафикстур. Для своих записей использовать существующий runtime; не скачивать второй Whisper и не обучать модель. Проверить права на каждый реальный материал и отсутствие секретов.

**T019/T020 — обработка.** Дать 03/04/06/09. Попросить медиаадаптер с проверкой контейнера, rotation, timeout и cancellation; отдельно job runner с lease/fencing. Приёмка: повторная доставка, crash, отмена и отсутствие звука. Простого `task.delay()` недостаточно.

**T043–T046 — ASR и предложения.** Попросить сначала FakeProvider и валидатор схемы, затем локальную расшифровку разрешённого примера, затем разрешённый внешний адаптер. Качество измерять на отложенных примерах, не переписывая expected под текущий результат модели. Не показывать метрику уверенности как гарантию.

## Запрос на проверку готового изменения

```text
Проверь diff задачи T___ и её критерии в docs/11-tasks.md.
Не переписывай код сразу. Найди конкретные ошибки поведения:
доступ между организациями, права, конкурентные изменения,
отмена/повтор, потеря данных, несоответствие API, отсутствие проверки.
Для каждой проблемы укажи файл/строку, воспроизводимый сценарий,
последствие и минимальное исправление. Отдели найденную ошибку
от непроверенного предположения. Затем запусти доступные проверки
и сообщи фактические результаты, включая то, что не запускалось.
```

После обзора человек решает, какое исправление применить. Изменение теста, которое просто делает ошибочный результат ожидаемым, не закрывает дефект. Повторный прогон нужен после последнего исправления, а не только до него.

## Работа троих без конфликтов

Предлагаемый процесс после создания репозитория: ветка `task/Txxx-short-name`, одно законченное изменение, краткое описание результата и проверки. Основная ветка должна сохранять рабочий ручной путь. Имена веток — рекомендация для будущей работы, сейчас они не созданы.

- A меняет frontend, B backend contracts/models, C processing/infra/tests. Это владельцы, а не запрет помогать друг другу.
- Изменение общей схемы/API сначала согласуется с B и A; обновляются документ, сервер, типы и fixtures.
- Два человека не запускают автоматические правки одних файлов одновременно. На разных checkout можно параллельно работать над независимыми задачами.
- Перед запросом модели осмотреть git status; после — diff. Не применять автоматический reset или удаление чужих файлов ради «чистоты».
- По пятницам выполнять сквозной сценарий из чистой среды, чтобы локальная работа одного участника не скрывала отсутствие интеграции.

## Что проверять в сгенерированном коде

Существование пакетов и поддерживаемых версий; отсутствие ключей в клиенте; обёртку внешнего SDK; валидность миграции с пустой и непустой БД; наличие tenant filters; server-side права; timezone и integer ms; atomic budget/quota; ограничения subprocess; отсутствие `shell=True` с пользовательским вводом; отсутствие raw HTML; правильный rollback; запрет автоматической публикации.

Сгенерированный текст для UX проверяет A, техническую точность шагов — мастер, безопасность доступа — B, соответствие источнику и ошибки обработки — C. Универсальной кнопки «ИИ всё проверил» в процессе нет.

## Короткая ежедневная запись

Каждый участник пишет: задача/результат, реально пройденные проверки, блокер, следующее конкретное действие. Время фиксируется приблизительно по задаче, включая чтение и исправление сгенерированного кода. Через неделю сравнить с оценками; производительность Astra учитывается фактическим завершением задач, а не количеством созданных строк.
