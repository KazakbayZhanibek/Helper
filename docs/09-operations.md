# Развёртывание, эксплуатация и расходы

[К полному плану](00-overview.md)

## Окружения

**Local:** каждый разработчик использует свои фиктивные данные, собственную БД и тестовый provider. Уже установленные системные медиаинструменты переиспользуются. На Mac с 8 ГБ одновременно запускать только необходимые сервисы; тяжёлое распознавание не запускать параллельно с несколькими контейнерами и моделями.

**Staging:** отдельный закрытый сервер, HTTPS, демонстрационные записи, настоящая схема хранения и выдачи видео. Только здесь проверять Nginx Range, real worker, timeout, backup и restore. Dev proxy не доказывает корректность production settings.

**Pilot:** отдельная БД, медиа, secrets и учётные записи. Не копировать рабочие материалы на ноутбуки команды без разрешения. Один сервер для первой организации — допустимое начальное упрощение, но это одна точка отказа, поэтому нужны резервные копии вне него.

Предлагаемая конфигурация для оценки стенда: 4 vCPU, 8–16 GiB RAM, 100 GiB SSD и отдельное место backups. Это гипотеза для нагрузочного прогона, не гарантированная достаточность для выбранного ASR. При локальном распознавании характеристики окончательно выбирать по peak RAM и времени реальных роликов, при внешнем — по требованиям передачи данных и бюджету.

## Переменные конфигурации

`APP_ENV`, `PUBLIC_BASE_URL`, `DJANGO_SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `DATABASE_URL`, `REDIS_URL`, `MEDIA_ROOT`, `TMP_ROOT`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `DEFAULT_FROM_EMAIL`, `STEP_PROVIDER`, `STEP_PROVIDER_API_KEY`, `ASR_PROVIDER`, `MAX_UPLOAD_BYTES`, `MAX_DURATION_MS`, `WORKER_CONCURRENCY`, `AI_DAILY_LIMIT_UNITS`, `BACKUP_DESTINATION`.

В `.env.example` только безопасные примеры, без рабочих значений. Валидатор settings останавливает запуск при неизвестной среде, пустом production secret, DEBUG=true на pilot или внешнем provider без ограничения бюджета. Настройки organization могут уменьшать общий предел, но не увеличивать его сверх разрешённого оператором.

## Процедура первого развёртывания

1. Утвердить сервер, регион хранения, владельца аккаунта, бюджет и правила доступа к данным.
2. Создать непривилегированного пользователя, закрыть наружный доступ к Postgres/Redis, установить обновления и проверить firewall.
3. Собрать образы из lock-файлов; worker и web используют одну версию кода. Проверить совместимость FFmpeg и ASR на fixture.
4. Подготовить закрытые тома original/playback/temp и отдельный backup target. Проверить права записи и свободное место.
5. Запустить БД и broker, применить миграции на пустой базе, создать организацию и первого admin служебной командой.
6. Настроить DNS/HTTPS, Nginx internal media, лимиты тела запроса и timeout передачи. Прямой доступ к файлам закрыть.
7. Запустить web, worker, recovery scheduler и garbage collector. Показать health только в предусмотренном объёме.
8. Проверить Django deployment checklist, вход/CSRF, invite/reset, upload, playback, ручную публикацию, reader и запрет чужого доступа.
9. Сделать backup и **реально восстановить его в отдельное окружение**. Сверить количество записей и hashes выбранных файлов.
10. Зафиксировать версию релиза, параметры и результаты. Только после этого приглашать пилотных пользователей.

Checklist Django является справочником проверки настроек, а не свидетельством того, что этот стенд уже развёрнут. [Официальная документация](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

## Обновление релиза

Один участник отвечает за выпуск, второй читает diff миграций и план возврата. Перед релизом остановить новые тяжёлые jobs, дождаться безопасной границы активных, сделать согласованный backup. Сначала применить совместимую миграцию, затем обновить web/worker, выполнить smoke. Старые и новые процессы не должны одновременно интерпретировать несовместимую схему job.

Для D1 допускается согласованное короткое окно обслуживания. Не обещать zero downtime. Обратный запуск старого image допустим только при совместимой БД; разрушительную миграцию не «откатывать» вслепую. Если нужна полная реставрация, учесть новые данные после backup и согласовать потерю с владельцем, а не удалять их автоматически.

## Backup и восстановление

Ежедневно в согласованное нерабочее время делать согласованную копию БД и медиа. Самый простой вариант D1 — краткий режим запрета записи, остановка принятия/завершения jobs, dump БД, snapshot/copy файлов, проверка manifest, затем возобновление. Если это окно неприемлемо, проектировать отдельный консистентный snapshot workflow до пилота.

Backup должен включать database dump, manifest storage keys/hash/bytes, media, версию схемы/релиза и необходимые конфигурационные идентификаторы. Секреты восстанавливаются через отдельный защищённый процесс. Копия на том же сервере не считается аварийным backup.

Шифрование копий, ограничение доступа, семь ежедневных поколений. Tombstones удаления ведутся в отдельном durable журнале, который не откатывается вместе с БД, и тоже резервируются. Проверять сохранность backup ежедневно, пробное восстановление — перед пилотом и после существенного изменения схемы/хранилища.

Порядок restore: закрыть внешнее чтение → поднять нужную версию среды → восстановить БД/файлы → применить все tombstones → повторно удалить запрещённые объекты → сверить manifest → smoke доступа/публикации → открыть сервис. Замерить реальное время. Цели RPO 24 часа и RTO 4 часа действуют только после успешного испытания.

## Наблюдаемость

Метрики: количество HTTP ошибок, API latency, очередь и возраст старейшей job, jobs по стадиям/исходам, heartbeat worker, disk free, RAM, незавершённые uploads, delete backlog, последний успешный backup, расходы provider. Логи содержат request_id/job_id/org_id и код ошибки, не контент.

Начальные пороги: диск свободен менее 20% — предупреждение, менее 10% — запрет новых uploads; queued job ждёт более 15 минут — диагностика очереди; отсутствие heartbeat более 90 секунд — recovery; backup старше 26 часов — инцидент; расход 80% дневного лимита — предупреждение, 100% — блок вызовов. Настроить каналы уведомления только после решения команды, не отправлять сообщения другим людям в рамках подготовки этого плана.

## Краткие инструкции при сбоях

| Симптом | Первые проверки | Действие | Как понять, что исправлено |
|---|---|---|---|
| Upload завис | Сеть, body limit, session state, temp disk | Отменить stale session; повторить передачу | Один asset, квота верна, temp очищен |
| Jobs не стартуют | Worker heartbeat, Redis, queued DB records | Восстановить зависимость; scanner повторно отправляет IDs | Очередь движется, дублей нет |
| Память закончилась | RSS, размер видео, количество процессов | Снизить concurrency/лимиты; повтор разрешённого job | Завершение контрольного ролика без OOM |
| AI 429/таймаут | Provider status, budget, Retry-After | Ограниченные повторы, затем ручной режим | Нет бесконечного цикла и скрытых расходов |
| Видео 403/404 | Membership, publication, storage key | Исправлять связь/конфиг, не открывать каталог публично | Reader получает только свою публикацию |
| Диск заполнен | Temp, orphan artifacts, backups на том же диске | Остановить uploads, уборка только подтверждённых orphan | Квота и manifest совпадают, рабочие файлы целы |
| Утечка доступа | Затронутые endpoints/IDs, логи без контента | Ограничить функцию, отозвать ключи при необходимости | Негативный тест воспроизводит и затем исключает сбой |
| Потеря сервера | Последняя копия и tombstones | Restore по процедуре | Сверены данные, доступ и удаление |

## Модель расходов

Не фиксировать стоимость провайдера по памяти. В T005/T044 записать дату тарифов, валюту, налоговые условия, лимиты и разрешённый месячный потолок. Пользователь не сообщил бюджет; покупка сервера или API этим планом не производится.

Формула планирования:

`C_month = hosting + backup_storage + media_storage + traffic + ASR_minutes × ASR_rate + input_tokens × input_rate + output_tokens × output_rate + email + reserve`.

Для локального ASR отдельной цены «за минуту API» нет, но учитываются вычисления, память, время обслуживания и ограничение очереди. Цена каждой **принятой** инструкции = расходы всех успешных и неуспешных попыток, делённые на количество принятых инструкций; бесплатные собственные часы отдельно измеряются, а не объявляются нулевыми затратами.

Пример нагрузки для расчёта, не тариф: 20 сотрудников × 5 записей × 3 минуты = 300 минут исходников в месяц. Фактический средний размер измерить на пяти роликах; умножить на количество, коэффициент производных, запас temp и число backup поколений. Видео в 500 MiB не считать стандартным размером каждой записи.

Платные вызовы резервируют максимальный допустимый расход **атомарно до отправки**. После ответа фиксируют usage и освобождают остаток; неизвестный исход не освобождается до сверки, иначе повтор может превысить бюджет. Расчёт в целых минимальных единицах валюты/токенов, не float. Хранить тарифную версию. Отдельная квота вызовов защищает даже при неизвестной цене конкретного ответа.

## Поддержка и передача ответственности

У компании один контакт, у команды один дежурный на неделю. Для обычного вопроса — запись в backlog; для доступа/данных — немедленный разбор. Не обещать круглосуточный SLA трём студентам. До пилота согласовать часы связи, окно обслуживания, способ вывоза материалов и процедуру окончания эксперимента.
