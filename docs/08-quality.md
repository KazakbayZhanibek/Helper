# Проверки, измерения и условия выпуска

[К полному плану](00-overview.md)

## Как фиксировать готовность

У задачи есть изменение, проверка и свидетельство: команда запуска, результат, ссылка на тест/скриншот или запись сценария. Успешный ответ GPT‑6 Astra не считается свидетельством. Тест не должен только повторять написанную функцию; он проверяет наблюдаемый результат или инвариант.

Для D0 можно полностью отключить внешние модели. Для D1 дополнительно требуется настоящий прогон согласованного провайдера на разрешённых данных. Fixtures проверяют интеграцию, но не доказывают качество распознавания или полезность текста.

## Наборы данных

Создать две организации A/B, в каждой admin/author/reviewer/reader; отдельный отключённый участник, незавершённое приглашение, истёкшая сессия. Объекты: инструкция без source, готовый ручной черновик, in_review, текущая публикация, новая рабочая версия при старой публикации, отозванная и удаляемая инструкция.

Медиа: короткое допустимое видео; портретное с rotation; без аудио; тишина; шум; HEVC с телефона; обрыв файла; ложный MIME; файл больше лимита; длительность/размеры выше предела; минимальное видео у границы; несовпадающие expected/factual bytes. Граничные большие файлы не хранить в Git: генератор создаёт их локально или проверка использует ограниченный поток.

Тексты: RU, KK, mixed; длинное название; HTML/скрипт; необычные Unicode; команды, похожие на prompt injection; неверные и чужие evidence IDs; ложные числа; пустой ответ; 31 шаг; внешние ссылки. Ожидаемое поведение прописать в fixture, а не оценивать «вроде нормально».

## Сквозные сценарии интерфейса

1. Admin приглашает автора и reader; приглашение принято; вход ведёт в нужную организацию.
2. Author создаёт инструкцию, загружает ролик, добавляет три шага, открывает preview, отправляет на проверку.
3. Reviewer оставляет блокирующее замечание, возвращает; author исправляет; reviewer отмечает шаги и публикует.
4. Reader на телефоне находит инструкцию, открывает второй шаг по видео, отправляет замечание с version/step.
5. Автор делает новый черновик, пока reader видит прежнюю публикацию. После новой публикации появляется сообщение о новой версии.
6. Reader открывает QR без сессии, входит и возвращается к инструкции; next URL не допускает внешний redirect.
7. Обрыв сети при сохранении/загрузке и истёкшая сессия приводят к понятному действию, без надписи «сохранено» до ответа сервера.
8. Для D1: реальный ASR → proposal → редактирование → review. Вторая проверка с отключённым провайдером проходит вручную.

Автоматизировать стабильные переходы и ошибки. Клавиатура, читаемость, видео с телефона и поведение на слабой сети дополнительно проверяются человеком. Матрица браузеров пилота: актуальный Chrome на Android, Safari на iPhone, Chrome/Edge на компьютере; точные версии и устройства записываются в протокол, не предполагаются заранее.

## Проверка ИИ

| Метрика | Как считать | Исходная цель D1 |
|---|---|---|
| Подтверждённость шагов | Шаги, чей смысл подтверждён источником / все предложенные шаги | ≥95% на проверочном наборе; все оставшиеся исправлены до публикации |
| Полнота | Найденные существенные действия / действия эталона | ≥80%; отдельно по языкам и записи |
| Числа/единицы/отрицания | Ошибки, меняющие операцию или результат | 0 неисправленных в принятой инструкции |
| Таймкоды | Начало/конец внутри source и позволяют увидеть нужный фрагмент | 100% структурно валидны; ≥90% оценены мастером как полезные |
| Экономия ручного времени | Время подготовки сопоставимого видео с ИИ против ручного | Медиана сокращения ≥30% на минимум 6 парных заданиях |
| Стоимость | Все попытки AI + ASR / принятые инструкции | Ниже согласованного предела T005; без выдуманной текущей цены |

Маленький набор не даёт статистической гарантии. Публиковать число проверенных записей, язык и распределение ошибок вместе со средним. В парном эксперименте менять порядок manual/AI между заданиями, иначе знакомство со вторым видео исказит результат. Не оценивать работу только самим автором prompt.

Если цель по экономии времени не выполнена, D1 остаётся экспериментом: улучшить вход, редактор или генератор и повторить на новых заданиях. Если KK существенно хуже RU, выпускать автоматическую функцию только для подтверждённого языка; ручное создание казахского текста сохраняется. Если есть неподтверждённые опасные действия, автоматический сценарий данного процесса не допускается в пилот.

## Производительность

Тестовый стенд описывается до измерения: CPU/RAM, диск, сеть, версии, размер базы. Для API: 10 активных виртуальных пользователей, 2 минуты прогрева и 10 минут измерения, смесь списка/чтения/поиска/сохранения. Считать p50/p95, ошибки и SQL count; загрузку и обработку измерять отдельно. Цели NF02–NF04 находятся в продуктовых требованиях.

Для медиа записывать upload time, prepare time, ASR real-time factor, peak RSS, размер производных и очередь. Проверить 1-, 5- и 10-минутные ролики. При превышении памяти ограничить ввод/модель или перенести обработку; не выдавать бесконечный retry за решение. Одновременное чтение видео и обработка не должны делать metadata API недоступным.

## Условия D0

- Все FR D0 из task list выполнены; SEC, upload, editor, publish, delete тесты проходят.
- Сквозной путь 1–7 выполнен на тестовом сервере с HTTPS.
- Нет открытых дефектов доступа, потери данных и публикации неверной версии.
- Проверены backup/restore, удаление и отзыв пользователя.
- Одна компания или независимый эксперт попробовал сценарий; если партнёра ещё нет, результат называется технической демонстрацией, а не пилотом.

## Дополнительные условия D1

- Реальные ASR и draft provider проходят разрешённый набор с отчётом по качеству и затратам.
- Provider выключается, лимиты действуют при гонке запросов, ручной путь сохраняется.
- Показаны failure/retry/cancel/stale proposal и восстановление после остановки worker.
- Мастер утвердил минимум пять инструкций; минимум пять читателей выполнили согласованное тестовое действие и дали обратную связь.

Число пять — масштаб начального эксперимента, не статистическое подтверждение спроса. Для обещания коммерческой пользы нужны повторное использование и готовность организации продолжать пилот.

## Классификация дефектов

P0: утечка/неверная публикация/массовая потеря данных — остановить доступ к затронутой функции, исправить и проверить. P1: основной сценарий не проходит, нет обходного пути — блокирует выпуск. P2: есть приемлемый обход, согласовать с пилотом. P3: косметика вне критического пути. Каждый дефект: шаги воспроизведения, expected/actual, окружение, IDs без приватного контента, владелец и проверка исправления.
